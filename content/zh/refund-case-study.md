# 企业AI项目怎么落地？从一个退款工单到Agent架构与验收标准

> 发布状态：草稿。案例是方案设计，不是已上线产品。可用于公众号、知乎或个人博客。

现在搭建一个能回答问题的AI Agent Demo并不难。但企业真正需要的是：查得到可信业务数据、分得清业务状态、知道什么时候必须交给人，以及能够用测试证明可靠性。

我正在公开整理 [Enterprise Support Agent](https://github.com/bob798/enterprise-support-agent)。第一个案例来自支付行业B2B技术支持：**商户反馈退款已发起，但消费者迟迟没有收到钱。**

## 1. 客户需要的不是退款规则，而是可核实的处理结果

技术支持可能需要确认订单编号、查询退款状态、检查账户条件，必要时协调渠道或运营人员。不同系统的状态含义与更新时间未必一致。单纯从知识库中找到一段退款规则，并不能证明某笔交易已经到账。

因此，这类工作的核心Job不是“回答一个FAQ”，而是**跨系统收集证据，判断下一步，并向商户给出可信解释**。

## 2. 先做Discovery，再谈模型选型

我把人工流程、涉及的系统、异常分支和需要人审批的操作整理进 [discovery.md](https://github.com/bob798/enterprise-support-agent/blob/main/examples/refund-not-received/discovery.md) 与 [workflow.md](https://github.com/bob798/enterprise-support-agent/blob/main/examples/refund-not-received/workflow.md)。

案例采用七维AI适配性评分，得到19/21分。**这是自定义筛选工具，不是外部认证，也不是ROI已验证。** 其作用是决定这个场景是否值得进入下一轮设计。

## 3. AI和确定性程序应当分工

拟议工作流为：

商户提问 → 识别问题并补全订单号 → 授权查询退款状态 → 按明确规则判断是否继续查询 → 生成有依据的答复，或结构化转人工。

语言模型适合处理自由文本、澄清缺失信息和组织表达；退款状态必须来自业务系统；路由、权限和高风险操作边界应由确定性机制约束。

**Agent不能凭语言模型推测资金事实。** 状态不明、查询失败或需要资金操作时，应明确说明证据不足，并交给有权限的人员。

## 4. 人工接管是设计的一部分

如果问题涉及渠道异常或多系统信息冲突，系统应交接订单号、已查到的状态、错误原因、原始提问和推荐的后续调查方向。这样人工不必从头重复收集信息。

这不意味着Agent已解决问题，而是把“查询结果”和“业务问题解决”区分开。

## 5. 先定义验收，再写代码

在 [acceptance.md](https://github.com/bob798/enterprise-support-agent/blob/main/examples/refund-not-received/acceptance.md) 中，我设计了意图识别、状态回复、异常升级、越权操作拦截、隐私保护、延迟与成本等验收标准，规划160个测试用例。

**这些目前是计划中的测试，尚无实际通过率和性能结果。** 后续会补充模拟接口、可运行Demo和评测数据。

## 6. 为什么要公开这个案例？

退款问题只是切入点。电商“签收但未收到货”、SaaS“API成功但状态未更新”、订阅“取消后仍扣费”，也可能共享一类工作模式：

**理解问题 → 查询多个系统 → 核实规则与证据 → 解释或执行允许的操作 → 必要时转人工。**

我希望验证的是：哪些工程方法可以跨行业复用，哪些又必须依据企业真实业务重新设计。
