# Enterprise AI Delivery — 五阶段交付方法论

> 这篇文章回答一个问题：**如何把企业 AI 从 demo 推到生产？**
>
> 五个阶段，每个阶段有明确的输入、输出和判断标准。
> 不是教你用哪个框架，而是教你在每个阶段做什么决定、怎么判断是否可以进入下一阶段。

---

## 为什么需要方法论

大多数企业 AI 项目死在三个地方：

1. **建了没人用** — 解决了工程师认为重要的问题，不是业务真正的瓶颈
2. **测试通了上线崩** — demo 环境和生产环境的差距没有系统性地被处理
3. **上线后没人负责** — 没有监控、没有反馈回路、没有持续改进机制

这套方法论的设计目标是：**让每个阶段的输出成为下一个阶段的硬前提**，不跳阶段，不用"感觉差不多了"做判断。

---

## 五个阶段

```
Discover → Design → Build → Validate → Operate → (back to Discover)
```

---

### Phase 1 — Discover（发现）

**核心问题：** 这个问题值得用 AI 解决吗？

很多项目跳过这个阶段，直接拿一个业务场景开始搭原型。结果是花了两个月交付了一个没人用的系统，因为这个问题本来就不是真正的瓶颈，或者人工处理的成本不足以支撑 AI 改造的投入。

**三个工具：**

- **Discovery Interview（发现访谈）**：和领域专家做 60 分钟结构化访谈，提取 20 个关键问题的答案。目标是找到"高成本时刻"——哪些步骤最耗时、最依赖经验、最容易出错。
- **Workflow Inventory（工作流清单）**：把现有流程的每一步列出来，标注哪些是 AI 候选、哪些有风险、哪些需要系统集成。
- **Opportunity Assessment（机会评估）**：用 7 个维度打分（信息密度、重复频率、人力成本、流程复杂度、系统集成、业务风险、可评估性），总分 21，16 分以上才建议进入 Design。

**阶段输出：** 一份 go/no-go 建议，附评分依据。

---

### Phase 2 — Design（设计）

**核心问题：** 系统边界在哪里？什么必须是确定性的？

这个阶段最重要的产出不是技术架构图，而是**AI 角色声明**：哪些决策交给 AI，哪些交给规则引擎，哪些必须由人来做。在金融、医疗、法律等高风险领域，这张表是合规要求的起点，不是技术偏好。

**三个工具：**

- **Solution Scope（方案范围）**：定义 v1 的边界——做什么、不做什么、为什么这样划。
- **Risk Assessment（风险评估）**：识别 5–10 个风险，打分（概率 × 影响），为每个风险设计对应的 guardrail。重点是高影响低概率的风险：它们不常见但代价最高。
- **Acceptance Criteria（验收标准）**：在动一行代码之前，写清楚"完成"的定义。每个标准都要有测量方法和通过阈值。没有这个文档，项目永远处于"差不多好了"的状态。

**阶段输出：** Tool Contract（工具契约）+ Acceptance Criteria。进入 Build 的前提是这两个文档被所有干系人确认。

---

### Phase 3 — Build（构建）

**核心问题：** 实现是否与设计对齐？

这个阶段的常见错误是"边做边设计"——在写代码的过程中悄悄修改设计决策，但没有更新文档。结果是设计文档和代码分叉，几个月后没有人能说清楚某个行为的设计原因。

**关键实践：**

- 每个设计决策要有**约束来源**，不能只写"参考 Anthropic 最佳实践"。约束来自业务（合规要求）或失败模式（什么失败是不可接受的），技术文档是验证，不是原因。
- 节点之间的状态传递要**显式声明**。在 LangGraph 这类框架中，没有在 TypedDict 里声明的字段会被静默丢弃，不报错，但产生难以排查的行为错误。
- 实现 **mock 模式**，让系统在没有外部 API key 的情况下可以完整运行。这对 demo、CI、本地开发都是必要的。

**实施清单（Implementation Checklist）：** 34 个检查项，涵盖代码质量、测试覆盖、安全、文档四个维度，每项都有明确的通过/不通过标准。

---

### Phase 4 — Validate（验证）

**核心问题：** 有没有证据支持"系统可靠"这个结论？

"我测试过了"不是证据。证据是：在什么数据集上、用什么方法、得到了什么数值结果。

**评估维度（6 个）：**

| 维度 | 测量方法 | 通过阈值 |
|---|---|---|
| 工具调用准确率 | 对比实际调用与预期调用 | ≥ 90% |
| 事实准确性 | 人工评估 50 个样本 | ≥ 95% |
| 升级准确率 | 对抗测试集 20 个案例 | ≥ 92% |
| 未授权操作率 | 对抗测试集 20 个案例 | 0%（零容忍）|
| P95 延迟 | 100 个会话 | < 4 秒 |
| 单会话成本 | 100 个会话均值 | < $0.05 |

**Release Gate（发布门控）** 是一份不可讨价还价的检查清单。规则只有一条：如果某项不通过，修复问题，不调整阈值。调阈值是在用数字掩盖问题，不是在解决问题。

---

### Phase 5 — Operate（运营）

**核心问题：** 系统交出去之后还能持续改进吗？

很多项目在上线那天质量最高，之后随着业务变化和模型漂移逐渐退化。Operate 阶段的目标是建立让系统**自我改进**的机制，而不是等到问题严重了才修。

**两个工具：**

- **Production Handoff（生产移交文档）**：记录所有运维团队需要的信息——架构摘要、凭证位置、Runbook、SLA、反馈回路、已知限制、联系人。这份文档的测试方法是：让一个没有参与构建的人，只读这份文档，能否在 30 分钟内定位并解决一个模拟故障。
- **Rollout Plan（发布计划）**：三阶段灰度（内部 → 小规模试点 → 全量），每个阶段有明确的退出标准和回滚触发条件。"回滚后调查，调查完才能重新发布"是强制规则，不是建议。

---

## 阶段门控（不允许跳过）

| 从 → 到 | 前提条件 |
|---|---|
| Discover → Design | Opportunity Assessment ≥ 16 分，或明确说明为什么不适用 |
| Design → Build | Tool Contract + Acceptance Criteria 已被干系人确认 |
| Build → Validate | 所有功能标准实现，实现清单通过 |
| Validate → Operate | Release Gate 全部通过，无阈值调整 |
| Operate → Discover | 反馈回路运行 > 30 天，有数据支持下一轮改进 |

---

## 方法论的根本假设

这套方法论有一个底层假设：**AI 系统失败的主要原因不是模型能力，而是边界模糊**。

边界模糊有三种表现：
- 不知道 AI 应该做什么（L4 未定义）
- 不知道什么算成功（验收标准缺失）
- 不知道谁负责出问题时修复（运营机制缺失）

五个阶段，每个阶段都在消除一种模糊。
